# 极影视第三方桌面客户端：阶段一研究与讨论稿

日期：2026-10-19。状态：研究初稿，产品布局和视觉方向待用户确认。没有进入 HTML 原型或 Rust/Slint 实现。

## 1. 定位、来源与覆盖边界

这是极空间既有影视服务的第三方桌面客户端，NAS 是片库和观看进度的主要事实来源。Rust 负责业务、异步任务和系统交互，Slint 是最终 UI；HTML 只用于后续设计确认。

已核对 `../adr/0002-first-release-scope.md`、`../spec.md`、`../architecture.md` 和 `../handoff.md`：LAN、现有片库及进度、基础播放、Windows 优先、个人自用已经确认，不重复要求用户选择。当前暂停实现、先研究设计，不代表撤销最终首版的基础播放范围。

仓库现状与历史交接不完全一致：实际存在 Cargo.toml、src/ 和 ui/；交接中的“没有应用代码”已经过时。本次仅核对存在性，没有运行应用、评估现有 UI 或证明接口/性能能力，也没有修改旧工程或历史文档。

公开资料研究不等于实机操作。来源以官方帮助、产品页和官方项目资料为主；宣传性能描述不是独立测量。没有足够版本与复现条件一致的用户反馈，不能推断各竞品卡顿的普遍程度或根因。NAS 产品的详细来源及版本限制见 [NAS 竞品来源笔记](nas-competitor-sources.md)。

## 3. 值得借鉴的交互与应避免的问题

以下均为本项目推荐，尚未获得设计批准。

1. 主导航只承担稳定位置：片库分类、可选首页、设置。搜索/筛选/排序放在内容工具栏，不变成多套重复导航。NAS 自定义分类优先于硬编码电影/电视剧。
2. 海报墙保持标题可见、图片槽尺寸稳定；优先标题、年份、观看进度，评分仅在字段可靠时显示。首轮不确定固定列数，后续在同一桌面窗口比较密度。避免全靠悬停才知道片名、整张卡片只有隐蔽菜单。
3. 详情优先呈现标题、简短元信息、播放/续播、具体剧集与进度，再呈现简介、演员和媒体规格。无数据时省略可选信息；缺失字段不伪造评分或播放能力。推荐独立详情页并保留返回位置，侧栏方案作为待讨论替代。
4. 续播和播放属于高频动作；连接与缓存设置进入设置页，次要信息用详情展开或菜单。错误就近显示并可重试，认证失效回登录；避免请求失败显示“暂无内容”、为加载弹阻断式对话框。
5. 收藏入口取决于真实读取/写入契约。若暂不支持，不造一个看似已同步的收藏按钮。管理、删除、重新刮削和回收站不进入首期；不用大轮播、全屏动态背景或强模糊挤占桌面内容区。

继续观看、最近添加、收藏和搜索的候选路径分别是：首页续播→播放；首页最近添加→详情；片库观看状态/收藏筛选→详情；工具栏搜索→结果→详情。首页可以暂不独立存在，其内容也可收敛到片库顶部；最终选项待确认。最近添加必须依据服务端添加时间，不能拿上映年份代替。

## 4. 卡顿分类：设计能改善什么，什么必须测量

| 体验问题 | 潜在原因，均未诊断 | 客户端方向 | 主测量边界 |
|---|---|---|---|
| 启动慢 | 初始化、凭据恢复、鉴权、首屏请求相互阻塞 | 先显示可操作窗口；恢复状态清楚；不等待整库海报 | 冷/热启动分别记录窗口可操作、首批数据和首屏海报时间 |
| 页面切换慢 | 重复请求、页面重建、状态丢失 | 返回保留分类、滚动位置和筛选；需要更新时局部刷新 | 已访问页返回时间与额外请求，区分冷访问 |
| 海报墙滚动卡顿 | 同时实例化过多卡片、解码/布局/GPU上传 | 可见行虚拟化、少量预取；固定图片槽，减少高成本特效 | 指定窗口与刷新率下记录帧时间分布、长帧及输入响应 |
| 图片慢/闪烁 | 原图过大、网络、重复下载或解码、缓存失效 | 优先可见缩略图，后台解码；原始字节/解码图各有容量限制；稳定标识避免重置图片 | 冷/热图命中、传输/解码时间、占位持续时间和回滚是否重闪 |
| 搜索/筛选慢 | 请求风暴、服务端慢、全量本地运算、旧结果覆盖 | 输入立即回显；短防抖、支持回车提交；只接纳当前查询结果；作用域明确 | 输入反馈、请求开始、响应与结果显示分段计时 |
| 条目越多越慢 | 整库获取、全量组件/排序、缓存持续增长 | 协议支持时分页；限制在途图片任务；大列表虚拟化；不以首次整库同步为前提 | 固定小/大数据集比较可见组件、内存、滚动与筛选耗时 |
| 网络/NAS 响应慢 | 连接、服务端处理、鉴权、协议/解析异常 | 可取消、可重试，保留可用页面；区分未请求/等待/失败/真实空库 | 请求耗时、HTTP与业务结果、解析后的条目数；不靠加载动画判定成功 |
| 视频启动/缓冲/播放卡顿 | 流准备、转码、传输、解码、渲染/字幕 | 区分正在取流、缓冲和失败；控制可响应；原生媒体路径 | 真实素材记录流准备/首帧、缓冲、解码路径和丢帧；与海报滚动分开 |

后台任务与 UI 线程分开，失效页面任务可取消或丢弃结果；但后台线程并不能自动解决过量并发、内存或 GPU 上传负担。限额缓存、批量 UI 更新等策略须在真实瓶颈出现的位置验证，不预建复杂框架。

工程依据：[Slint ListView 文档](https://docs.slint.dev/latest/docs/slint/reference/std-widgets/views/listview/)说明可见项实例化；这不自动证明自定义多列海报墙已虚拟化，也未核对仓库实际锁定版本的支持细节。[Slint 图片异步加载讨论](https://github.com/slint-ui/slint/discussions/5140)提供后台工作与 UI 派发线索；[Google 的长任务说明](https://web.dev/articles/optimize-long-tasks)和[图片懒加载实践](https://github.com/GoogleChrome/web.dev/blob/main/src/site/content/en/fast/lazy-loading-best-practices/index.md)仅用于 HTML 原型，不把 Web 指标当作 Slint 性能证明。

建议后续采用一个可重复场景：同一台 Windows 机器、固定窗口/刷新率、固定数据，分别冷缓存和热缓存，浏览→滚动→详情→返回→搜索；真实 NAS 请求单独计时。大数据量原型可用 1,000/10,000 条模拟元数据考察退化趋势，它不证明 NAS 支持该规模。长时间使用另外观察内存是否趋于稳定、缓存是否遵守上限，不能用短演示替代。

建议将“本地点击/键盘反馈 P95 ≤100ms”作为待讨论目标；60Hz 场景关注 16.7ms 帧预算及长帧，但不以平均 FPS 作为唯一标准。搜索结果、海报完成和视频首帧先测基线，不承诺统一阈值或提升比例。HTML 只能证明其环境下的交互与布局，Slint/真实播放必须以后单独验收。

## 5. 建议首期 UI 范围与未知约束

建议核心页面：连接/登录；分类片库；影片/剧集详情；应用内播放状态与基础控制；精简设置。首页是否独立待确认。加载、空库、错误和重新认证是这些页面的状态，不另扩一套功能。

继续观看与最近添加是高价值候选；搜索及基础筛选/排序是本次建议增补，旧 Spec 未承诺完整搜索系统，是否纳入原型须在阶段一确认。收藏待协议证据后决定，默认不做独立收藏系统。播放在最终首版范围内；后续原型只模拟播放交互，不接真实流或上报 NAS 进度。

待技术核对：可用的搜索作用域、分页与排序字段；续播/最近添加/收藏列表语义及权限；图片缩略图尺寸与鉴权/有效期；详情缺失字段和版本差异；原生播放引擎与 Slint 表面的集成限制。接口目录中的静态封装不是这些能力已可用的证据。本轮不以调研之名接入 NAS 或变更播放器。

本轮讨论聚焦三个决定：默认进入续播首页还是完整片库；详情是独立页还是侧栏；最影响使用的两类卡顿。推荐默认片库、详情独立页、优先证明输入响应和滚动；深浅主题、海报尺寸等在主结构确定后比较，不在本轮默认选深色。

## 6. 协议可行性门槛补充（2026-10-19）

用户新增约束：先利用既有 REA 记录调查有价值功能的实现依据，缺口由指定 GPT-5.6 Luna / max 子智能体补查；不能先完成 HTML 再发现关键功能没有数据来源。因此当前停在协议可行性调查，不开始 HTML 或修改正式 UI。

现场重新计算安装包 SHA-256 为 `3b645f03ff9b9e72bc1ee46819e3da81b9fbf4259bf5d79bd849ed3d45dcff28`，与既有 manifest 和核心路径报告一致。可复用同版本安装包证据；这不更新 NAS 固件版本或证明运行时结果。

已有 `reference/nas-video-api-catalog.json` 的记录已能纠正“当前 Rust 未接入就等于无法实现”的判断：

| 功能 | 已有静态依据 | 必须保留的边界 |
|---|---|---|
| 片库搜索 | `/zvideo/search/index` 使用 `key_word`，页面消费 `data.collection` 和 `data.video`；`/zvideo/search/suggest` 消费建议词 | 不把编辑/匹配流程的 `/search/local` 当成完整主搜索；演员与番号检索语义另证 |
| 演职员与按人浏览 | `/zvideo/collection/person` 使用 `collection_id`，页面消费 `actor/director/writer`；`/zvideo/person/collection/list` 消费 `data.list/count` | 当前 Rust 模型未接线；人的稳定 ID、返回字段和具体片库数据完整性需进一步核对 |
| 排序与筛选 | 普通列表调用构造 `field/sort/seen/collection_type` 并合并 `listParams` | 每个取值、作用域和当前固件兼容性需核对；不复用旧 `system=7` 作为默认 |
| 收藏 | 存在 `/favorite/list` 的调用和 `/favorite/add`、`/favorite/delete` 包装 | add/delete 原 catalog 没有调用点，参数、状态语义仍需补证；本轮不执行写入 |
| 最近添加与播放历史 | `/video/v2/lately` 与 `/video/v2/playlist` 有分页调用和列表消费 | 播放历史不自动等于“未看完”的继续观看列表；排序语义与续播位置读取另证 |
| 独立番号字段 | 目前不能从已核对的 catalog 确认 | 不能把标题中出现编号当成独立番号字段、专用索引或精确查询能力 |
| 详情侧栏、密度、隐私显示 | 属于本地展示状态，可复用已有分类/详情/播放数据 | 是待实现客户端交互，不是现有 NAS 功能，也尚未运行验收 |

核对位置：`/search/index` 调用位于 `35697.82b0cbe4.js` UTF-16 偏移 15907；演职员与按人浏览位于 `14318.9b9586db.js` 偏移 72424、151316；列表参数位于 `32779.f5626b76.js` 偏移 22757。以上由旧 NAS 公开脚本 catalog 复核，不冒充安装包内新发现或真实请求通过。当前 Rust 的 `NasClient` 和 `CollectionItem/CollectionDetail` 也已核对，新增功能尚未接入，音字幕切换仍有明确未支持提示。

随后指定子智能体完成了补查，主会话复核了搜索、收藏和 history 原文及源文件哈希。新增结论：全局搜索包含 `data.person`；收藏动态调用补全为 `{collection_id,classification_id}`，成功分支更新 `is_fav`；详情 `history` 有 `last_video_id/play_duration` 等读取链。独立番号字段仍未知。上表记录的是初次 catalog 复核，补查后的最终静态依据和限制以 [UI 功能可行性报告](../../reference/reverse-engineering/ui-feature-feasibility-2026-10-19.md) 为准。

进入原型前，每项关键交互要有“数据来源、请求/响应依据、当前实现缺口、未验证项”。纯展示功能可据本地交互设计；关键数据能力没有足够依据时应先缩减或暂停该项。静态依据充分表示具备开发候选路径，不等于实测成功。

用户随后授权继续，已完成 18 次真实 NAS 只读请求：标题命中原片；演员和按人作品列表返回数据；收藏、最近添加和筛选结构也已取得。详情的续播字段存在，但新旧版本分别位于顶层与 `history`；本次 5 个历史抽样未取得正数续播位置，持久化与播放恢复仍未验证。收藏写入、组合筛选排序效果和番号专用能力没有因接口返回 200 而升级为已通过。详见上方可行性报告最新状态；没有开始 HTML 或修改正式工程。

阶段门槛：用户确认首期 UI 范围、主页面关系和设计方向，且关键功能可行性缺口已有处理决定后才进入 HTML 原型；明确体验并批准原型后才做 Slint 映射。本文和来源笔记均不是批准记录。
