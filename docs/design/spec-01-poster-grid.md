## Problem Statement

Windows 原生片库未还原已确认的暗色 Apple HTML 原型：同一行 Collection 卡片宽度悬殊，部分封面极窄、部分横向铺满，封面被严重裁切，长标题进一步干扰浏览。用户无法稳定扫视和选片。截图确认该现象；实现使用按内容偏好分配的网格列、最小宽度约束和固定图片高度，缺少统一列宽与 2:3 几何约束。具体布局求解贡献仍应在修复前复现核实。

## Solution

将片库恢复为等宽、比例稳定、随窗口调整列数的海报墙。源图尺寸、长标题、图片加载结果均不得改变卡片几何。以已确认 Apple HTML 原型为视觉基准，用非敏感数据在真实 Windows Slint 窗口验收。

## User Stories

1. As a 片库用户, I want 同行卡片等宽, so that 我能快速扫视 Collection。
2. As a 片库用户, I want 封面框保持 2:3, so that 横竖源图不会破坏排列。
3. As a 片库用户, I want 封面按比例居中裁切, so that 图片不被拉伸。
4. As a 片库用户, I want 长标题省略而不撑开列宽, so that 列表保持稳定。
5. As a 桌面用户, I want 窗口变窄时减少列数, so that 卡片不会变成细条。
6. As a 桌面用户, I want 大窗口提高可见条目数, so that 空间得到有效利用。
7. As a 片库用户, I want 图片未加载和失败时保留同尺寸占位, so that 浏览位置不跳动。
8. As a 键盘用户, I want 焦点可见且能打开 Collection, so that 我能连续选片。
9. As a 鼠标用户, I want 整张卡片点击行为一致, so that 能可靠进入详情。
10. As a 大片库用户, I want 滚动加载保持响应, so that 图片工作不会阻塞选片。
11. As a 片库用户, I want 区分已加载数量和片库总数, so that 50 条不会被误当成全部内容。
12. As a 用户, I want 原生截图与已确认原型对照, so that 错位不会在交付后才发现。

## Implementation Decisions

- 仅修改 Collection 网格、海报卡片及其必要的视口/图片协调。保留 Rust + Slint、NAS 作为事实来源、现有鉴权和播放路径。
- 列宽由内容可用宽度、统一间距和目标卡片尺寸决定；相同视口同行宽度一致，2:3 封面高度由卡片宽度派生。禁止源图固有尺寸和文字 preferred size 主导列宽。
- 约 1440×900 的标准预览对照 HTML 约 7 列；900×640、1440×900、2560×1380 分别验证合理列数、无水平溢出、无遮挡。不得为固定 7 列牺牲最小窗口。
- 使用现有图片缓存与过期请求机制；先复现并记录基线，再决定是否需要按行虚拟化或分页，不因修样式重建缓存框架。
- 同步图片替换不改变卡片几何。标题与年份/类型的层级、间距、圆角以已确认原型为准，弱化整卡装饰边框。
- 加载条数与服务端总数分别显示；未支持后续页时明确范围，不能伪装成完整片库。

## Testing Decisions

- 用户已确认主证明为真实 Slint 窗口：同一组脱敏 Collection 包含横图、竖图、超宽图、超长标题、缺失/失败封面；在三个目标窗口尺寸捕获原生渲染并与 HTML 对照。不得上传私人片名、封面、NAS 地址或凭据。
- 必须在旧实现重现列宽差异，再用同一输入证明修复；检查等宽、2:3、无拉伸/溢出、异步图片完成前后位置稳定、鼠标和键盘打开行为。渲染证据覆盖外观，避免用源码字符串或组件树快照替代。
- 复用现有应用协调器依赖注入和 Media library 集成测试入口；只有模型/交互契约发生变化才扩展相关行为用例。已有用例未检查渲染几何，因此不能证明本缺陷已修。
- 记录代表性条目数、加载/滚动过程和资源基线；无实测不得承诺加速比例。编译检查只是前置条件。

## Out of Scope

播放器、登录协议、NAS 写操作、刮削、全库索引、主题重做、macOS 验收和公开发布。
