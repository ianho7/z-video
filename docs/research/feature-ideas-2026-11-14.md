## 0. 约束前提

- 最小实现，不预建通用框架（`AGENTS.md` 实现约束）。
- renderer 只拿 opaque `mediaId` 与 renderer-safe DTO，任何路径/URI 与解码工作都在 main/worker。
- 文件系统监听与自动扫描目前明确在范围外：`docs/local-library/ux-rework-spec.md:318` 把"自动 watcher、文件系统监听"列为非目标。
- 现有扫描、播放、观看账本的状态机在 `docs/local-library/state-machines.md`；新功能必须服从"单一状态载体"规则。

## 1. NFO / 文件变更自动感知

### 现状

- **没有任何监听**：依赖只有 `fast-xml-parser` 与 `koffi`，无 `chokidar`、无 `fs.watch`。
- 触发扫描的入口只有三个：添加文件夹、来源卡"重新扫描"、"重新扫描全部"；启动不做全量扫描。
- NFO 缓存按 `size + mtime` 失效，因此**只要能触发扫描，改过的 NFO 一定会被重读**；缺的只是触发。
- 全树遍历成本可观：2,000 文件约 3 秒，20,000 文件约 30 秒（`docs/local-library/completions/05.md`）。
- 扫描结果的 `updatedFiles` 是"重新见到的文件数"，不是真实变化数（`upsertMedia` 的分支只看是否新建）。做自动感知后这个语义会立刻变成噪音。

### 判断

**瓶颈不是监听，而是扫描粒度。** 改一个 NFO 就全树重扫 30 秒，不可接受；先要有"只处理变化"的能力，监听的收益才成立。

### 可选触发机制

| 方案 | 成本 | 命中率 | 已知问题 |
|---|---|---|---|
| 窗口聚焦 / 回到片库时触发 | 低 | 高（覆盖大多数真实使用） | 仍需增量能力，否则同样全量扫 |
| `fs.watch` 递归 + 防抖 | 中（Electron 内置，无新依赖） | 本地盘好；**SMB/网络盘经常不报事件** | Windows 递归 watch 的重命名/句柄语义需实测 |
| 定时轮询 stat | 低-中 | 网络盘唯一可靠方案 | 全库 stat 也不便宜，需按目录分片 |

### 建议切片

1. **增量扫描 API**：按目录/路径重扫，返回精确的 `imported / updated / unchanged / removed / degraded` 计数，并区分"NFO-only 变化"与"视频指纹变化"。
2. **聚焦触发**：窗口重新获得焦点或从详情/播放器返回片库时，做一次轻量校验（先 stat NFO 与视频的 size/mtime，不读 XML）。
3. **监听补齐**：本地盘 `fs.watch` + 防抖；网络盘走低频轮询。两者共用同一套"变化 → 增量扫描"入口。

### 未确认

- SMB/网络盘在 Windows 上 `fs.watch` 的实际行为（需实测，不能假设）。
- 自动扫描与现有 `scanRefreshQueued` 刷新机制的竞争：扫描中用户停在详情页时，最后的提交目前不会被消费（见 `state-machines.md` 扫描 UI 一节）。

## 2. 连续分诊（Slidebox / ClipSweep 风格）

### 已有能力

`docs/local-library/tickets/14-cleanup-keep-terminal.md` 落地的 A3 检查模式已经具备：从整理队列打开单个候选 → 播放 → 键盘决定 keep / snooze / delete-candidate → 关闭播放器时弹出决定 → 失败可重试。

### 缺口

- 决策后不会自动进入下一个（当前必须回到队列再点）。
- 没有单键决策（K/S/D）。
- 没有撤销上一步。
- 没有会话汇总（本次分诊了多少、标记了什么）。

### 建议

把 A3 从"单例"扩成"会话"：`idle → triaging → deciding → summary`，复用现有播放协调与清理标记写入路径。撤销只需记录上一步的 `{mediaId, previousState}`，因为本应用**从不删除文件**，误操作风险低。

规模 S–M，纯 renderer + 一个显式状态机，不新增后端。

## 3. 播放器内核与体积（分享二）

### 现状

- `libmpv-2.dll` 121,006,592 字节；Windows 候选包 503,138,932 字节 / 231 个常规文件（`docs/local-library/completions/05.md`）。
- Electron 自身约占 90–100MB，属于平台固定成本。

### 判断

**不建议换引擎。** 现有播放链路（原生子窗口、overlay、进度、字幕/轨道、关闭终态）都围绕 libmpv 建成，换内核等于重做整条链路，收益不明。体积优化的现实路径是**定制构建**：裁 debug symbols、不需要的编码器/DVD/蓝光/网络协议，保留 D3D11 与（未来 macOS）VideoToolbox。

### 待定

需要用户给出体积目标（例如"安装包 < 350MB"）才值得立项；否则记为可选 spike，不排期。

## 4. 原生控件残留

### 实测结果

| 项 | 现状 |
|---|---|
| 滚动条 | **`::-webkit-scrollbar` 规则 0 条**，完全是 Chromium 默认样式（最明显的残留） |
| `<dialog>` | 已样式化（圆角/内边距/背景），`::backdrop` 需确认 |
| `input[type=range]` | 播放器里为透明覆盖层 + 自绘 thumb，已处理 |
| `<details>/<summary>` | 有类名样式，但原生三角标记仍在（`index.html` 的添加菜单、技术详情、支持格式） |
| 原生 tooltip | `title=` 共 5 处，会弹 Windows 原生提示 |

### 建议

一条"外观一致性"小 Ticket 收口：滚动条（普通/hover/暗色）、`summary` 标记替换、原生 tooltip 改自绘、`::selection` 与 focus ring 统一。工作量小、感知强。

### 待补充审计

右键菜单、文本拖拽选择、滚动回弹、`<input type=number>` 等尚未逐一核对，实施前应补一次全量清单。

## 5. 进度条里的"精华片段"

### 必须先拆开的四件事

| 你在 B站 / Pornhub 看到的 | 数据来源 | 本地单用户能否复现 |
|---|---|---|
| B站"高能进度条" | 弹幕密度 | 否（没有弹幕数据） |
| Pornhub 播放热区 | 聚合观众播放/拖拽分布 | 否（没有人群数据） |
| 音频波形 | 离线解码算峰值 | 可以，但要整轨解码 |
| 场景切换密度 | 帧级分析 | 可以，成本高 |

结论：**"最精华片段"在单人本地库里没有现成信号**。能诚实做出来的只有下面三条路。

### 方案 A：自观看热区（建议先做）

用本地遥测画出"你自己反复回到/常看的区间"——Pornhub 模型的 N=1 版。现有播放链路每 10 秒上报位置（`player.ts` 的心跳与 position 事件），只需把位置落成粗桶（例如 1% 一格）并聚合。

- 成本：M；需要 schema 变更（新表或 `media_history` 新列）与一次数据模型评审。
- 冷启动：没看过的影片没有数据，必须有空态，不能装作有热区。
- 诚实边界：它回答的是"我常看哪里"，不是"哪里最好看"。

### 方案 B：真音频波形（替换现有假波形）

现在进度条后面那条波形是**装饰性 SVG**：`src/renderer/index.html:347` 的 `.player-wave` 是一条固定正弦路径，`src/renderer/styles.css:372-373` 用 `clip-path` 跟着 `--progress` 裁剪。它是视觉占位，不含任何真实数据。

要做真波形需要离线解码整轨、抽峰值数组、缓存。解码必须发生在 main/worker（renderer 拿不到路径）。可选实现：libmpv 解码导出 PCM、或引入最小的 FFmpeg 组件。成本 L，且只解决"看节奏"，不解决"精华"。

### 方案 C：内容启发式

响度包络（爆炸/音乐段）或场景切换密度。技术上可做，但与主观"精华"差距大，容易制造误导，建议只做 spike，不承诺。

### 建议顺序

A（自观看热区）→ B（真波形）→ C 仅实验。进度条最终形态可以是"波形底图 + 热区高亮"叠加，但两者分开交付、分开验证。

## 9. 仓鼠型用户画像：如何快速判断"看还是删"

### 画像

收藏速度远高于消费速度；决策疲劳让"选片"本身成为负担；记不住已有什么，导致重复下载；对隐私敏感；偏好其实稳定（演员/厂牌/类型/画质），但库里没有结构化表达；删了又后悔。

### 判断

对这类用户，最有价值的不是"判断好不好看"，而是**降低单次决策的认知成本**，以及**让重复与遗忘可见**。因此产品重心应从"库管理"偏向"决策引擎"。

### 候选能力（按性价比）

| 能力 | 说明 | 依赖 |
|---|---|---|
| 三秒卡片 | 6 帧 contact sheet + 时长/大小/分辨率 + 单键 K/S/D + 自动下一个 | G2 |
| 30 秒试看 | 卡片内静音播放随机/开头 30 秒，比静帧更能判断 | 播放链路复用 |
| 内容指纹去重 | 帧感知哈希 + 时长 + 音频指纹，识别重编码/改名/多清晰度 | 新解码任务 |
| 版本折叠 | 同一内容多版本折成一张卡，默认保留最高质量 | 去重结果 |
| 后悔率追踪 | 删除后同指纹再出现即记一次"后悔"，用于校准规则 | 去重 + 账本 |
| 随机放映 | 从"未看"里按时长过滤抽一部，解决选择困难 | 账本 |
| 队列化/到期 | "想看"变成有期限队列，到期即"要么看要么删" | 账本 + 提醒 |
| 配额制 | 每来源存储预算，超限强制分诊；显示 GB/小时成本 | 现有清理规则 |
| 文件名解析 | 常见命名模式 → 结构化字段；解析失败进"元数据待补"队列 | 本地规则 |
| 演员/厂牌聚合 | 以人为单位浏览（有 40 部、看过 3 部），而非文件名 | 解析结果 |
| sidecar 覆盖 | 允许 `.zv.json` 覆盖元数据，不改原文件 | 只读边界内 |
| 一键打点 | 观看时按 M 标记"这里好"，成为跨会话累积的章节点 | 播放 + 账本 |
| 隐私模式 | 缩略图模糊、任务栏预览遮挡、留痕清理、恐慌键 | renderer/main |
| 导入前置提示 | "该厂牌已有 12 部，9 部未看"；可选一进一出 | 账本 |

不建议：自动删除、评分式"值得看"打分（主观且易误导）、强制配额阻塞导入。

## 10. 可穿戴联动（心率）

### 可行性

| 设备 | 路径 | 结论 |
|---|---|---|
| 心率带（Polar H10 等） | 标准 BLE Heart Rate Service `0x180D` | 可行，最稳 |
| 部分运动表（Garmin/Coros/Wahoo，开启"广播心率"时） | 同上 | 可行，取决于型号设置 |
| Apple Watch | 不对外广播 HR；HealthKit 仅 iOS | Windows 侧不可行 |
| Fitbit / 多数手环 | 无 BLE HR 广播，走厂商云 API | 不可行（且违背本地优先） |

Windows 侧需 WinRT BLE GATT；Electron 没有内置 BLE，需要一个 native 桥或小型 sidecar 进程。这与"不新增运行时/不预建框架"冲突，建议先做**POC 验证**再决定。

### 有价值且不越界的用法

1. **参与度热区**：把"相对静息心率的变化 + 播放位置"聚合成分段强度曲线，作为"精华片段"的生理信号，并明确它只是"生理反应较高"，不是"内容更好"。
2. **会话边界**：HR 上升 + 播放开始 → 会话开始；长时间无变化 → 提示停止并落账本。
3. **与自打点交叉验证**：比较"手动标记"和"高心率区间"，学习个人偏好。

### 风险与边界

- 健康数据极敏感：默认关闭、本地加密、显式同意、可一键删除、绝不联网。
- 生理信号受运动/咖啡因/情绪干扰，不能作为内容质量结论。
- 可能强化成瘾，需要配套观看时长提醒。
- 兼容性碎片化：只承诺标准 BLE HRM，不按品牌做适配。

### 现成项目调研（2026-11-14，GitHub）

关键发现：**不需要逆向协议**。小米/华为的部分手环支持"心率广播"档，把心率按标准 BLE Heart Rate Service（`0x180D`）广播出去，任何标准接收端都能订阅，无需 auth key。

| 项目 | 语言 | 星标 | 说明 | 可用性 |
|---|---|---|---|---|
| [Tnze/miband-heart-rate](https://github.com/Tnze/miband-heart-rate) | Rust (MIT) | 145 | 小米手环 10「运动心率广播」Demo，用 `bluest`，支持 Windows/macOS/Linux | 最接近本项目的参考，最近仍在更新 |
| [PT-nt107/MiBandHeartRateMonitor](https://github.com/PT-nt107/MiBandHeartRateMonitor) | Python (MIT) | 3 | Bleak 读心率，要求手环 4/5/6/7 开启 HeartRateBroadcast | 证明广播档覆盖 4–7 |
| [Eryux/miband-heartrate](https://github.com/Eryux/miband-heartrate) | C# (MIT) | 69 | Windows 10 客户端，小米手环 2/3/4；4 需要 auth key | 老路线，说明旧型号要逆向 |
| [leolittig/huawei_ble](https://github.com/leolittig/huawei_ble) | Dart | 2 | 华为手表/手环 BLE 心率（Android）；代码直接用标准 `0000180D` 与 `00002A37` | 证明华为设备同样暴露标准服务 |
| [wasimcodex/180D](https://github.com/wasimcodex/180D) | Kotlin (MIT) | 3 | 标准 HRM 服务接收端 | 标准服务的参考实现 |
| [Gadgetbridge](https://gadgetbridge.org/) | Java | — | 开源手环管理（含小米 auth key 机制） | 协议与兼容性参考，不直接复用于 Windows |

### 华为手环 9 结论（2026-11-14 核实）

- 华为官方支持页《华为手表/手环心率广播》确认：设备「设置 > 心率广播」可单独开启，开启后持续测量并把心率分享给支持心率广播的设备与第三方应用；也可在锻炼中保持广播。无该菜单项即机型不支持。
- `leolittig/huawei_ble` 直接订阅标准 `0x180D` / `0x2A37`，说明华为穿戴走标准 BLE HRM，不是私有协议。
- 关键注意：该仓库扫描用 `withServices: []`（扫全部）再按服务过滤，说明**设备不一定在广播包里 advertise `0x180D`**。Web Bluetooth 的 `filters: [{ services: [...] }]` 依赖广播内容，可能搜不到；POC 应改用 `acceptAllDevices: true` + `optionalServices: ['heart_rate']`，由主进程在 `select-bluetooth-device` 里按名称筛选。
- 代价：心率广播是持续测量，手环耗电会明显增加；息屏/断连后是否自动停止需实测。

Electron 侧路径：

- **Web Bluetooth**：Electron 的 `webContents` 有 `select-bluetooth-device` 事件，renderer 可调用 `navigator.bluetooth.requestDevice({ filters: [{ services: ['heart_rate'] }] })`，主进程负责选设备。**不需要 native 模块**。
- 备选：`@stoprocent/noble`（WinRT 后端，仍在维护）或 `noble-winrt`，但需要为 Electron ABI 重新编译。

需要实测的点：`file://` 是否满足安全上下文、是否需要 bluetooth 权限处理器放行、广播模式是否每次都要在手环上手开、采样率与延迟、断连重连、与其它 BLE 设备共存。

建议 POC：最小 Electron 窗口 + 设备选择 + 订阅 `heart_rate_measurement`，记录首次连接耗时/断连恢复/开启步骤/资源占用；通过后再谈产品化。

## 11. 产品与用户理解

- **核心 job 是降低决策成本与后悔率**，不是把库变大。
- **只读是信任资产**：应用从不删除/移动文件，只标记与交接给资源管理器；这个边界应保持。
- **可度量指标**：决策吞吐（每分钟处理数）、后悔率（重下/恢复）、未看占比、每 GB 的"被观看分钟"。
- **反目标**：社交/云端排行、自动删除、连续打卡（对仓鼠型用户会放大内疚与收藏焦虑）、任何需要上传片库的推荐。
- **护城河是本地口味画像**：从 keep/观看/标记/心率派生，只在本机；驱动排序、去重与"值得看"提示。
- **诚实边界**："值不值得看"是主观的；产品能做的只是把可观测信号（时长、清晰度、厂牌、你的历史、重复情况）摆到台面并降低操作摩擦，不能假装懂品味。
- **风险**：分诊机器可能反过来鼓励"先囤着以后再清"。缓解手段是导入前置成本提示与配额，而不是强制阻塞。

## 12. 推进计划（阶段划分）

### 原则

1. **先收敛状态与验证缺口，再叠用户可见功能**：renderer 现在还是"多布尔 + 多 hidden"的隐式状态机，任何 UI 功能都在上面加变量；先做 Ticket 15 能把后续每次改动变便宜。
2. **worker 与 renderer 两条线可并行**：变更感知（G1）在 worker/DB，外观与分诊在 renderer，文件不重叠。
3. **每个阶段产出 Ticket + 完成记录**，沿用 `docs/local-library/tickets/` 的格式与验收项。
4. **规模是相对量级**：S ≈ 半天到 1 天，M ≈ 2–4 天，L ≈ 1 周以上（单人、含测试与记录，不含真实媒体/硬件验收）。

### 阶段

| 阶段 | 内容 | 规模 | 依赖 | 退出条件 |
|---|---|---|---|---|
| **P0 收尾** | Ticket 15（renderer 状态收敛：单一视图来源、epoch 拆分、错误恢复派生、详情 reopening、卡片复用清理）；补齐上次按需跳过的窗口冒烟（player / player-overlay / appearance / safe-storage / resume） | L | 无 | 视图可见性由单一来源派生；`test:window` 与 `test:local-library-app` 全绿；未验证项清单清零或明确延期 |
| **P1 快赢** | G4 外观一致性（自定义滚动条、`summary` 标记、原生 tooltip 换自绘、selection/focus 统一）；观看打点（播放中一键标记 → 章节点，跨会话累积） | S + S | P0（打点需稳定播放态） | 无原生控件残留清单；打点可写入/读取并在进度条显示 |
| **P2 变更感知** | G1：增量扫描 API（按目录重扫 + 精确 `imported/updated/unchanged/removed` 计数）→ 聚焦触发 → 本地盘 `fs.watch` / 网络盘轮询 | M | 无（可与 P0/P1 并行） | 改动 NFO/增删文件后，回到片库无需手动扫描即可看到正确结果；20k 库的自动扫描不做全量重扫 |
| **P3 连续分诊** | G2：三秒卡片（6 帧 + 元数据 + K/S/D + 自动下一个）、决策预算（每会话上限）、撤销、会话汇总 | M | P0、P1 打点可选 | 一次会话可连续处理 ≥20 个条目且可撤销；不新增误删风险（应用仍只标记不删除） |
| **P4 库存治理** | 内容指纹去重（先轻量：时长+大小+文件名相似；后帧哈希）、版本折叠、后悔率追踪、队列化/到期、配额可视化、文件名解析与演员/厂牌聚合 | M–L | P3（复用分诊 UI） | 重复条目可识别并折叠；库存指标（未看占比、每 GB 被观看分钟）可见 |
| **P5 热区与波形** | G3：自观看热区（位置分桶，schema v5）、进度条热区渲染；真音频波形 spike →（可选）离线峰值数组与缓存 | M（波形 L） | P1 打点、P3/P4 数据 | 热区有真实数据才显示，空态明确；波形 spike 给出解码耗时与缓存体积结论 |
| **P6 探索** | 心率 POC（华为手环 9，六条验收）→ 若通过再做"生理热区"；libmpv 定制构建 spike（需体积目标） | S 调研 | 体积目标 / POC 结果 | POC 六条全过才进产品；否则记录结论并关闭 |

### 建议的并行排布

```text
P0 ──┬── P1 ── P3 ── P4 ── P5
     └── P2（worker，可提前并行）
P6 等目标与兴趣，不占关键路径
```

- P0 是唯一的全局阻塞项，建议先做。
- P2 与 P0/P1 不共享文件，可同时开一条子代理通道。
- P5 的数据依赖 P1 打点与 P3/P4 的观看量；没有数据前只做设计不做实现。

### 决策闸门

- **G-A（P0 之后）**：renderer 收敛是否让窗口冒烟稳定通过；若不然，先修再开 P1。
- **G-B（P3 之后）**：分诊会话的完成率与撤销率是否证明方向成立；否则回到"单卡整理"而不是继续加功能。
- **G-C（P5 之前）**：打点/热区样本是否够（建议 ≥30 次会话），否则不渲染热区。
- **G-D（P6 之前）**：心率 POC 六条验收；体积需要用户给出目标数字。

### 最小路径（如果只投入两周）

P0 → P1 → P2。理由：状态收敛降低后续成本，外观与打点是立刻可感知的收益，变更感知是最高频的日常摩擦。分诊与去重留到下一阶段。

### 本阶段明确不做

- 自动删除/移动文件（破坏只读信任边界）。
- 云端同步、社交、排行榜。
- 依赖厂商云的设备集成（华为/小米云端 API）。
- 需要上传片库的推荐。

## 14. 执行口径与决策记录（2026-11-14）

### 估算口径

旧估算按"人类工程师-天"，与实际执行方式不符。对照事实：Ticket 06–14、16 共 10 票、37 个文件、2231 行新增，4 通道并行约 2 小时墙钟。

- **1 批 ≈ 2–5 小时墙钟**，含 typecheck、定向冒烟、完成记录；不含真实媒体/GUI 人工验收。
- 阶段批次：S0 两批；S0.5 一批 + 汇总；S1 一批；S2 两批；S3 两到三批；S4 三到四批；S5 两到三批；S6 一批。
- 不可压缩项：窗口冒烟的墙钟、既有 flaky 测试的修复、新能力（关键帧抽取、音频解码）的正确性验证。

### 完成定义（DoD）

1. `npm run typecheck` 通过。
2. 受影响的单测通过。
3. 涉及渲染的跑对应窗口冒烟。
4. 改了既有断言 → 逐条报备旧/新/理由。
5. 完成记录落 `docs/local-library/completions/`。
6. 未验证项显式标注，不写成已实现事实。
