# 本地片库扫描与详情数据修复 — 2026-11-06

## 范围

本 lane 只覆盖 local-library database / worker / IPC / shared contract。没有修改 renderer、preload 或 `ipc-channels`，没有启动桌面 GUI，也没有访问私人 NAS。

## 已确认根因

- worker 在每个视频条目完成 `upsertMedia` 后提交 SQLite，并发送 `running` progress；扫描期间已提交行可以被 `list` 查询。
- `LocalLibraryDatabase` 的缓存 `state` 只在初始化、扫描结束或显式 `refreshState()` 时更新；progress 事件本身不会刷新它。
- 原 `local-library:list` IPC handler 在等待 page 之前读取 `database.getState()`，因此扫描中即使 page 已经看到新增项，返回的 `sources` 仍可能是旧的空数组。
- renderer 当前只把 progress 写入扫描文案，是否在 progress 期间触发有界 `list` 刷新由 UI lane 负责；不能在 worker 中按每个文件推送 state。

## 变更

1. `local-library:list` 先查询 page，再调用一次 `refreshState()` 返回安全 source summary。这样 UI 的节流刷新能看到已提交条目和当前来源计数，不产生逐文件 state 刷新。
2. `LocalMediaDetail.playback` 作为可选 renderer-safe 字段加入 shared contract。worker 先确认请求 `mediaId` 对应的媒体行，再按同一 opaque ID 读取 playback；无 playback 时省略字段。
3. 扩展现有 local DB owner smoke，验证详情 playback 的 mediaId、位置、时长和保存后更新结果；同步更新 local-library contract 文档。

## UI handoff

UI lane 需要在 `onScanProgress` 的 `running` 事件上做有界/节流的 `localLibrary.list` 刷新；后端已保证该查询能读到已提交行并返回最新安全 source summary。不要把 progress 事件扩展为 worker 逐文件 state 推送，也不要把 source root 或路径加入 DTO。
