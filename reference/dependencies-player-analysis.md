# Zspace native proxy, player and IPC boundary

## Findings

The desktop shell loads a **local login page**, then selects the NAS web desktop at the native proxy's returned HTTP origin plus `/home/`. Its web proxy is an FFI wrapper around `sdk/libzrpc_x64.dll`; it is separate from the loopback TCP control server used by `uzplayer/UZPlayer.exe`.

The normal video path launches UZPlayer with a percent-encoded JSON server address, display information and username. The media URL and authentication context are delivered subsequently over TCP. Electron-to-player messages use `len=<base64-character-count>{<base64(JSON UTF-8)>`; the Electron receive handler instead parses each incoming TCP data callback directly as JSON.

Static PE imports establish a Windows x64 **UZPlayer → VLCQt → libVLC** chain, with Qt6 and Windows C/C++ runtime dependencies. `playsdk.dll` is separately bound by Electron for audio. Its presence next to UZPlayer does not establish that UZPlayer imports it.

This pass does not repeat the player HTTP catalog. See [player-static-evidence.json](player-static-evidence.json), whose `background.js` SHA-256 matches the source read here. Login credential-exchange APIs and recycle-bin business APIs are outside this narrowed native-boundary pass; the findings below must not be mistaken for a complete implementation of those features.

### Service request serialization and direct-IP mode

`background.js @c4561800`:


This is an application-defined JS-to-DLL argument envelope: timestamped JSON → AES-256-GCM ciphertext → base64 → native `libzrpc_start_service`. It is **not** the player TCP framing and does not establish the network wire protocol. `de`/`he` come from SHA-256 of a deterministic PRNG-derived string in the immediately preceding code; this wrapper does not append a GCM authentication tag. Native interpretation was not decompiled or tested.

`background.js @c4562058` parses native string results using `JSON.parse`; empty results become `{code:500,msg:"调用SDK方法时发生错误"}`. Service success is tested against `code:200`.

Direct-IP selection uses `libzrpc_set_private_network_access(ip,port,isV6,isPort5050)`. Its ordinary wrapper has defaults `port=5055,isV6=false,isPort5050=false`. The saved-login flow supplies `loginInfo.deviceIp`, `loginPort`, whether mode is `ipv6`, and whether the input port equals 5050. An integer result `<=1` aborts the direct-IP branch. IPv6 priority and force-tunnel settings are passed separately. `ForceExternal.txt` under userData adds `connect_mode:1` to ordinary service requests.

One nonobvious distinction is explicit in `background.js @c4566211`:


## 4. UZPlayer selection, launch arguments and media handoff

### Executable and helper lifecycle

`background.js @c4753135` chooses the initial TCP port and platform-specific executable:

```js

```

The Windows path literal is `uzplayer\\UZPlayer.exe` at `background.js @c4753294`; the joined path replaces `app.asar` with `app.asar.unpacked`. On an ASCII installation path it runs from that unpacked directory. On a non-ASCII path, the initialization block at `background.js @c4894840` copies the player directory to the Public-profile-derived `ZSpace/uzplayer` directory and rewrites `Fa` to its `UZPlayer.exe`. Consequently the eventual executable is not necessarily inside the installed application's resources directory. This describes packaged code; no copy was performed here.

`background.js @c4753922` builds a sibling `VlcPreload.exe` path and invokes:

```text

```

A successful command callback sets `global.VlcPreloaded=true` (`background.js @c4754173`). Video launch checks this flag (`@c4788033`). Native helper strings corroborate `/playsdk.dll` at `uzplayer/VlcPreload.exe @b14464` and `initPlay` at `@b14520`; string presence alone does not recover the helper's full call sequence.

There is **no media URL or token in this normal launch command**. The promise polls every **200 ms** for any incoming player data (`Ya>0`), and gives up after **40,000 ms**. If an existing socket has received data within **3000 ms**, the code reuses it and sends new playback information instead of launching another process. This is a data-receipt check; it does not verify decoded video output.

On a TCP connection the main process sends an initial `f_type:"100",s_type:"0"` packet (`background.js @c4786919`) containing `apiHost`, loopback server coordinates and cookie fields `app:"video"`, encoded token, `plat:"pc"`, NAS ID, public IP, version, device ID and device. See the existing player JSON evidence for the HTTP wrappers that produce those values.

A separate third-party-player setting path is present. `_c` selects it only when configured and collection/classification arguments are present; after resolving a play URL it calls `ba` with `"<configured-player-path>" "<media-URL>"` (`background.js @c4790718`). This path receives a URL as a command argument and is distinct from UZPlayer's TCP bootstrap. It must not be used to describe the default UZPlayer launch.

`background.js @c4921864` also intercepts newly opened `/home/player?vid=...` URLs, decodes `vid`, and routes them to `_c({path:n,title:o})`, denying the default window opening. This is another static shell entry point to the same launch path.

## 5. Loopback TCP server and message framing

`background.js @c4771954`:

```js
pc=e=>{ja=Ia.createServer(),ja.listen({host:"127.0.0.1",exclusive:!0,port:e}),...
```

`Ia=n(42)` resolves to Node's `net` external (`background.js @c158097`), so this is a **raw TCP server**, not an HTTP route or WebSocket. It initially chooses a port in **13600–13619**, retries with `e+1` on listen errors (`background.js @c4786850`), and therefore can end outside that starting range. The successful port is saved as `playerPort` inside `<userData>/zspace.conf`. Main initialization calls `pc(ka)` at `@c4896222`.

On connection, the handler assigns the socket to `za`, increments `qa`, and sends the initial cookie/origin packet. On end, close or socket error it clears `za`. Native strings `InitTcp start cmd not tcpInfo read zspace.conf` (`uzplayer/UZPlayer.exe @b1298040`) and `/AppData/Roaming/%1/zspace.conf` (`@b1298088`) support a native fallback configuration path, but do not establish its parsing or precedence.
